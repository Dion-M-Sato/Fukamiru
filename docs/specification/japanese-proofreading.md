# 日本語校正

## 現行profileと実行条件

`translation.japanese_proofreading_profile = "llmjp33b_adopt"`は、
LLM-jp-4.1 33B thinking BF16 / highによる節単位の局所校正を選びます。
対象は原稿生成ワークフローです。翻訳のローカル後編集用モデルとは分離しています。
共有既定値の`local_v32`と、独立確認を含む`llmjp33b_high`は別profileです。
既存Runの保存済み選択と旧方式は維持します。新規Runは作成時のprofileを保存します。
33B方式の未設定・不適合を8Bや量子化モデルへの切替で補いません。

HF Jobsまたは適合する専用サーバーを使用します。実際のモデル・BF16形式、
65,536以上の1要求contextと`Reasoning: high`のテンプレートを送信前に検証します。
生成枠を含む入力長は実トークナイザーで確認します。
HFではモデル・ランタイムのrevisionとハッシュも固定します。

## ノードの責務

1. `diagnose_japanese_prose`：CPUで原文HTML、節・段落ID、編集可能なtext slot、
   保護本文、書名・引用などの固定要素を凍結する。モデルは呼ばない。
2. `redraft_japanese_paragraphs`：対象節と前後各最大1段落を渡し、各節1回で
   診断・日本語の理由・局所before/after案をまとめて受け取る。全文は再送しない。
   LLM-jpに全文改稿、再審査、代案探索、失敗した節の再生成を依頼しない。
3. `review_japanese_sections`：CPUで実在する原文アンカー、重複、固定要素、括弧、
   DOMとIDを検査する。原文にない誤記の指摘は`excluded_corrections/source_mismatch`として残す。
   Sol mediumは変更対象段落をまとめて1回読み、内容変更・文の破損だけを採用または保留で確認する。
   保留は実変更と重なる原文・候補の引用と日本語の理由を必要とし、修正文は返せない。
4. `japanese_surface_quality_gate`：Lunaが既存の執筆・引用表記規定を適用する。
   書名等の固定要素と採用された語彙を保持し、語彙の書換えは検査で拒否する。
5. `reconcile_candidate_context_after_proofreading`：実際の文別evidence useから
   引用の実現先を再構成する。節で利用可能だっただけの資料を引用扱いにしない。
   その後、既存rendererが脚注と参考文献を作る。
6. 最終本文処理：採用表現を保持する。原典未確認などの確認状態を人間レビューへ送る際も、
   編集可能slotからの完全一致削除に限定し、理由・段落・削除前後のhashを保存する。
   実質的な条件、限界、否定、反証、人間保護本文、引用と脚注は維持する。

LLM-jpの学習に基づく語法判断を、実測コーパス頻度や「文法誤りの証明」がないという理由で拒否しません。
専門語、学術的な語彙、必要な中心語の反復と接続を保ちます。
Solは日本語モデルの語法の好みを再判定せず、内容追加・意味変更の検査を担当します。
修正案の件数に推論回数の制限を転用しません。

## 保存と失敗

指示・入力・最終schema・model/decoding・source hashを含む指紋で結果を保存します。
同一の完了結果は空結果を含めて再利用します。HFの受領と停止の契約は
[HF Jobs管理](hf-proofreading-jobs.md)を参照してください。
未解決の機械検査は結果を保持して適用を止め、schemaや原文検査を弱めません。
LLM-jpへ再送したり段落全体を黙って旧稿へ戻したりして解消しません。
原案、適用案、不適用、保留、人間の判断は区別して保存します。

最終schemaの各objectとrequiredを再帰的に検査します。
UIのフロー図は実行可能な定義から生成し、現行profileの64ノード・79辺と照合します。
構造保持と受領の検証は、モデルの語法判断すべての正しさを保証するものではありません。
